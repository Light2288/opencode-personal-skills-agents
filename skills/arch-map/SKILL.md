# Architecture Map

Create a grounded, human-readable snapshot of the current repository at
`docs/architecture/map.md`.

## Write Boundary

This workflow remains skill-only. It does not need a dedicated agent because
the host agent already has the tools and permission needed to create the single
`docs/architecture/map.md` artifact, and map generation does not process
untrusted document instructions. Its delegated `explore` scan is read-only and
is unrelated to the write boundary; the host agent validates and writes the
completed map. Use a dedicated agent only when a workflow needs a permission
fence or model the host agent lacks.

The write scope is nevertheless explicit: create or replace only
`docs/architecture/map.md` and create its parent directory when absent. Do not
write elsewhere under `docs/architecture/**`.

## Inputs

- Optional argument: `force`.
- Treat only an exact `force` argument as forced regeneration.
- Operate on the current workspace and current Git HEAD.

## Phase 1 — Check Freshness

1. Read `docs/architecture/map.md` when it exists.
2. Obtain the current SHA with `git rev-parse HEAD` when the workspace is a
   Git repository. Use `not-a-git-worktree` when it is not.
3. Parse the map's `HEAD SHA` and `Key Paths` metadata.
4. Classify the map as stale when any condition holds:
   - the map is missing;
   - its stored HEAD SHA differs from the current SHA;
   - any missing referenced key path is found;
   - generation metadata is absent or malformed.
5. Without `force`, reuse a current map and report that no repository scan was
   needed. Stop without rewriting it.
6. With `force`, bypass reuse even when the map is current.

Direct `/map` use regenerates a missing or stale map. `spec-plan` has separate
warning-only behavior and must not invoke regeneration automatically.

## Phase 2 — Scan Once

Delegate one compact scan using the `task` tool with `subagent_type: explore`.
Ask for evidence-backed findings covering:

- modules, responsibilities, and entry points;
- dependency direction, boundaries, and observed cycles;
- data stores and persistence mechanisms;
- external services and integrations;
- test layout, frameworks, and fixtures;
- build and test commands read from manifests;
- key paths that substantiate the map.

Request a structured digest, not raw file dumps. Do not infer components that
the scan cannot support.

If explore delegation is unavailable, use in-context `glob`, `grep`, and
`read`. Use read-only shell commands only when the specialized tools cannot
answer the question. State in the result and generated marker that the
in-context fallback was used.

## Phase 3 — Render Safely

1. Create `docs/architecture/` if absent.
2. Build the complete map in memory before replacing an existing map.
3. Verify every listed key path exists at generation time.
4. Use an ISO 8601 timestamp including timezone.
5. Write the exact structure below, adapting table rows to observed evidence.
6. Report whether the map was created, regenerated as stale, forced, or reused.

Do not modify application code, reorganize modules, or add architecture
enforcement. Dependency information is descriptive and human-verified. Report
observed cycles where applicable, but do not add executable cycle checks.

## Exit Conditions

Success requires either:

- a current map reused without a scan; or
- a complete map written after a successful scan, with current metadata and
  valid key paths.

If scanning fails or evidence is incomplete, retain the existing map and
report the blocker. Never replace it with partial or fabricated content.
